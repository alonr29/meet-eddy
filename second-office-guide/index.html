לפני שמתחילים

משרד AI שני אינו "עוד צ׳אט". הוא שכבת ייעוץ עצמאית שמוסיפה זווית נוספת — בעוד שהמערכת הראשית נשארת בעלת הבית של המשתמש, הזיכרון והפעולות.

🌱 הדוגמה שתלווה אותנו לאורך המדריך

נניח שיש לכם בוט בשם "נעמה" שמסייע בניהול גינה קהילתית: תזכורות השקיה, פגישות מתנדבים ורשימת משימות. אתם רוצים להוסיף משרד ייעוץ שני שיעזור בהחלטות מורכבות — למשל, האם לפתוח חלקה חדשה או לשנות חלוקת עבודה.

  • משתמשים ונתיבים מאושרים מוגדרים במפורש; אין "גישה לכולם" כברירת מחדל.

פרק רביעי
הלב של המדריך

בנייה צעד־אחר־צעד

עשרה שלבים, לפי הסדר. כל שלב נשען על הקודם — אל תדלגו קדימה.

01

תכננו את המשרד לפני שבונים אותו

התחילו בקבוצה קטנה של תפקידים בדיוניים: Coordinator לניתוב, Security Advisor, UX Advisor, Method Teacher ו־External Auditor. כל תפקיד מקבל רשימת מקורות מותרת וחתימת פתיחה קבועה.

למה חתימה קבועה? כדי להוכיח שהתשובה הגיעה ממסלול מאושר, ולא רק מטקסט שנראה משכנע.

02

בנו registry סגור

אל תאפשרו למשתמש לבחור שם תפקיד חופשי או מקור ידע חופשי. הגדירו רשימה סגורה של role + mode + signature + sources. מי שמבקר את המערכת צריך להישאר מחוץ לרשימת היועצים.

03

ארזו ידע קפוא ומאומת

במקום למשוך קבצים בזמן ריצה, ארזו snapshot: רשימת קבצים מאושרים, hash לכל קובץ, גודל מרבי ומסמך provenance. השירות טוען רק מה שמופיע ברשימה.

04

הגדירו חוזים קשיחים

בקשה ותשובה אינן "JSON כללי". הן חוזה. הלקוח והשרת חייבים להסכים בדיוק על שמות השדות, סוגיהם, המגבלות והמשמעות.

דוגמת בקשה
{ "version": "v1", "request_id": "<UUID>", "question": "<QUESTION>" }
דוגמת תשובה
{ "version": "v1", "request_id": "<UUID>", "status": "ok",
  "role": "<ROLE>", "answer": "<TEXT>", "sources": ["<SOURCE>"],
  "safety": { "read_only": true, "stored": false } }

מה זה אומר בפשטות: כל הודעה נראית תמיד אותו דבר — אותם שדות, באותו סדר. אם משהו חסר או שונה, השרת דוחה מיד.

05

חתמו על כל בקשה

חתמו ב־HMAC על method, path, זמן, request ID ו־hash של גוף הבקשה. בצד השרת בדקו key ID, חלון זמן קצר, UUID תקין ומניעת replay. שמרו סוד נפרד לכל ערוץ עתידי.

06

בנו את הליבה בלי רשת

השאירו את לוגיקת הניתוב, החוזים והוולידציה טהורים: בלי משתני סביבה, בלי Telegram ובלי קריאות HTTP. הזריקו את המודל כתלות. כך אפשר לבדוק כמעט הכול מקומית.

07

הוסיפו Adapter צר למודל

ה־Adapter צריך לבצע בקשה אחת ל־Responses API, ללא כלים, עם store=false, timeout משותף ומגבלת גודל. אל תתנו לשגיאות ספק המודל להיחשף ללקוח או ליומן.

08

עטפו ב־Gateway קטן

חשפו בפיילוט רק health endpoint ו־consult endpoint. דחו routes לא מוכרים, headers כפולים, גוף גדול, חיבורים איטיים, redirect ו־proxy סביבתי. השתמשו ב־HTTPS וב־allowlist מדויקת של host.

09

חברו את הבוט בגשר דק

הבוט לא צריך להכיר את הידע הפנימי או את מפתח ספק המודל. הוא בודק הרשאה, מסנן קלט, חותם בקשה אחת, מאמת את התשובה ומציג אותה. המסלול הישן נשאר כבוי.

10

הוסיפו ייעוץ דו־מוחי — רק אחרי שהגשר יציב

לשאלות חשובות, המערכת הראשית והמשרד השני מגבשים עמדות עצמאיות במקביל. שופט מציג מסקנה, הסכמות, מחלוקת וצעד הבא.

חובה לשמור את שתי העמדות המפורשות — כדי למנוע עיגון שקט של צד אחד.

תרחישים שליליים שחובה לבדוק

  • חתימה לא נכונה, request ID חוזר וזמן ישן.
  • שני headers באותו שם או JSON עם key כפול.
  • URL עם redirect, host לא מאושר או proxy סביבתי.
  • תשובה גדולה מדי, schema חסר או מקור לא מאושר.
  • ביטול בקשה באמצע והוכחה שחיבור HTTP נסגר.
  • תצורה חסרה: פיצ׳ר הייעוץ נכשל בבטחה והבוט הרגיל ממשיך.
  • שאלה עם הקשר קצר ושאלה עם הקשר מלא; מודדים זמן ולא רק סטטוס.

פריסה מבוקרת, ניטור ו־Rollback

סדר פריסה בטוח

הקימו Sidecar נפרד — תהליך אחד ו־replica אחד בפיילוט; אל תוסיפו אותו לתהליך הבוט.

הזינו סודות בממשק הפריסה בלבד — אל תעתיקו ערכים לצ׳אט, לקובץ או ל־Git.

בדקו health — רק הוכחה שהשירות חי.

בדקו smoke חתום — הוכחה שהבוט יכול להגיע ל־Gateway עם אימות תקין.

פרסו את הבוט עם flag כבוי — היכולות הקיימות נשארות הפעילות היחידות.

בדקו יכולות קיימות — תזכורות, פעולות והודעות יום־יומיות חייבות להישאר תקינות.

הפעילו פיילוט מוגבל — רק משתמש וצ׳אט פרטיים מאושרים, ורק באישור מפורש.

📊

מדדים בטוחים לניטור

קוד תוצאה כללי (200 / 401 / 429 / 502 / 503) · זמן כולל של הבקשה, בלי תוכן השאלה · מספר נסיונות fallback, circuit breaker או retry · סוג כשל קבוע (למשל timeout או missing required label), ללא exception text חופשי.

↩️

Rollback לפני שמפעילים

כבו את feature flag של הייעוץ · הפעילו מחדש את שירות הבוט · אם יש חשד לחשיפת סוד: עצרו את ה־Sidecar וסובבו את הסוד בשני הצדדים · אל תשנו את המערכת הראשית, הזיכרון או הפעולות כדי לבטל פיילוט ייעוץ.

נספח ג · Starter Prompt לפרויקט חדש

💬 מדביקים בשיחה חדשה

אני בונה מערכת ייעוץ AI שנייה לצד בוט קיים. המשרד השני חייב להיות read-only, מופרד מהבוט ומהמפתחות שלו, מאומת בבקשות חתומות, עם knowledge snapshot מאושר, חוזי בקשה ותשובה קשיחים, feature flag כבוי כברירת מחדל ותוכנית rollback. הוביל אותי צעד־אחר־צעד: תכנון, בדיקות מקומיות, Gateway, smoke חתום, פריסה מוגבלת — ורק אחר כך הפעלה. אל תבקש ממני מפתחות או סודות בצ׳אט.
